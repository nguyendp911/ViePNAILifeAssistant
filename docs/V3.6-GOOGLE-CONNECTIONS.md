# V3.6 — Connected Services

## Implemented
- Google OAuth 2.0 authorization-code flow for a **confidential gateway** (not stored on iOS). Random one-use state bound to the current authenticated account expires after 10 minutes.
- Separate, least-privilege scopes: `gmail.readonly` and `calendar.events.readonly`.
- Tokens encrypted with AES-256-GCM before storage in the already tenant-scoped persistence layer (PostgreSQL JSONB in hosted mode or JSON in local testing); access tokens refreshed server-side.
- Read latest 10 Gmail message metadata/snippets, and next 25 calendar events. No sending, editing, deleting, or invitations.
- iPhone Profile > Connected Services provides Connect, View and Disconnect actions; auth opens Google consent in system browser.

## Set up Google Cloud
1. Create a Google Cloud project, enable Gmail API and Google Calendar API, and configure OAuth consent and test users (as applicable).
2. Create **Web application** OAuth credentials, configure redirect URI `https://YOUR-HOST/v1/integrations/google/callback` precisely.
3. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, and a new random 32-byte hex `GOOGLE_TOKEN_ENCRYPTION_KEY` in gateway secrets.
4. Serve Gateway behind HTTPS, with database and durable secrets. Do NOT paste these server secrets into the iOS app.
5. In the app, sign in and connect Gmail or Calendar separately. The callback shows a browser success page; return to the app to view data. Disconnect stops local access; for Google-side complete revocation, users can remove access in their Google Account security settings.

## Security, current limitations, and release gates
- Prototype OAuth state lives in Gateway process memory: restarts during authorization invalidate consent; multi-replica deployments require a shared, expiring state store.
- Token encryption key must be securely backed up and rotated deliberately; losing it will prevent decrypting stored tokens.
- The current disconnect deletes local tokens, but does **not** invoke Google token-revocation endpoint.
- Store data remains tenant-scoped, but production deployment requires database migrations, backup, audit, rate limiting, and independent penetration tests.
- This build does **not** provide account synchronization with Gmail/Calendar until actual OAuth credentials and provider approval are configured.
- Google OAuth verification may be required for restricted Gmail scopes and for publishing externally.
- Never put Gmail content in LLM prompts automatically. Require explicit user action and permission before AI processing.

## API
- `GET /v1/integrations/google` → `{configured, connections:{gmail,calendar}}`
- `POST /v1/integrations/google/start` `{service:"gmail"|"calendar"}` → `{authorizationURL}`
- `GET /v1/integrations/google/callback?code=...&state=...` (Google browser callback)
- `GET /v1/integrations/google/gmail` → `{items:[{id,subject,from,date,snippet}]}`
- `GET /v1/integrations/google/calendar` → `{items:[{id,summary,start,end}]}`
- `POST /v1/integrations/google/disconnect` `{service:"gmail"|"calendar"}` → `{disconnected:true}`

No Python dependency. AI API configuration remains optional and independent of OAuth.
